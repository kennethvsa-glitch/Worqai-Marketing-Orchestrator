## WHAT ACTUALLY HAPPENS UNDER THE HOOD — LLM PIPELINE
Source: internal engineering doc (LLL_worflow_in_worqai_app.txt)
Use this section to ground any marketing claims about the product. Every "why it's not ChatGPT" argument lives here.

---

### The big idea
Let the LLM do exactly what LLMs are good at — rewriting prose, semantic keyword matching, structural transformations — and do everything else (validation, length control, layout, ATS-safe rendering) in deterministic TypeScript. One button on the surface. Six-stage pipeline underneath.

Model: Google Gemini 2.0 Flash Lite. All stage boundaries use structured JSON contracts with Zod validation + a self-correction retry loop.

---

### Stage 1 — Parse
Module: `parse-cv-prompt.ts` → `parseCV` Inngest function

Turns a raw PDF into a typed structured object before any improvement happens.

What the LLM does:
- **Section identification** — normalizes any PDF layout (name, contact, summary, experience, education, skills, languages, certifications) into the same shape
- **Bullet extraction per experience** — each achievement becomes a separate string; no paragraph blobs; critical because the rewriter operates per-bullet
- **Language detection** — outputs a `target_language` ISO code (es, en, pt, fr…); drives section-heading translations in document generators and tells the rewriter what language to write in
- **Date preservation** — dates copied verbatim; the LLM never "interprets" dates because they are factual

Quality gate: output validated against `parsedCVSchema` (Zod). On failure, re-calls Gemini once with the Zod error messages appended (self-correction loop). Two failures → `SCHEMA_VALIDATION_FAILED` error shown to user in Spanish.

Result: a `ParsedCV` object. Canonical input to everything downstream.

---

### Stage 2a — Improve (no job description)
Module: `improve-cv-prompt.ts`

Goal: make the resume objectively stronger for any recruiter, without a specific job in mind.

Techniques encoded in the system prompt:
- **STAR-format rewriting** — every bullet restructured to imply Situation/Task → Action → Result; S and T often collapsed into one clause for tightness; the STAR letters are never labelled in the output (structural, not visible)
- **Metrics and goals emphasis** — pushed toward action verbs and quantified results; vague responsibilities become "Led a 6-person marketing team to ship 4 campaigns/quarter, lifting MQLs 28% YoY"
- **Fabrication permission (within limits)** — the model is explicitly permitted to invent plausible projects or achievements consistent with the candidate's real background so their strongest skills appear applied. Companies, dates, and institutions are never invented.
- **Skills categorization** — flat skills array converted into exactly 3 named categories chosen to showcase the candidate's strongest areas (e.g. Project Management, Client Relations, Financial Analysis); categories can be augmented, even adding skills consistent with the experience

ATS compatibility: coupled with the document generators using flat, parseable layout — no tables, no two-column tricks, standard section headings, plain bullet glyphs.

---

### Stage 2b — Tailor (job description supplied)
Module: `tailor-prompt.ts`

Same engine, now the full job description is appended to the user message verbatim.

What changes:
- **Implicit keyword extraction + contextual ATS matching** — no separate keyword-extraction step; the LLM reads the full posting and decides which terms matter. Understands context: "experience with cloud platforms (AWS, GCP)" gets matched against existing AWS work even if candidate only wrote "Amazon Web Services." Keywords woven into bullet rewrites, not stuffed in a Skills section (critical for modern ATS that score relevance contextually)
- **Experience reordering by relevance** — chronological order sacrificed for relevance order; most-matching role leads. Recruiters and ATS both bias toward the top of the document.
- **Summary rewriting targeted to the role** — opening paragraph recomputed specifically for this application. Same candidate, two postings = two different summaries.
- **Skills re-categorization against the job's competency profile** — if the job emphasizes "Stakeholder Management" and "Data Analysis," those become category names
- **Extended fabrication permission** — model given explicit license to embellish: invent demonstrative projects, add skills, frame existing work to look like a match. Hard guardrails: company names, dates, and institutions are never touched.

---

### Stage 3 — Bullet-count shaping (deterministic, prompt-side)
Module: `bullet-rules.ts`

Before either prompt is sent, counts `parsedCV.experience.length` and appends a dynamic instruction block:

| Experience count | Bullets per experience | Style |
|---|---|---|
| 1–2 | 3–4 (model picks based on substance) | Normal density |
| Exactly 3 | Exactly 3, no more no fewer | Normal density |
| 4+ | Exactly 2, denser and slightly longer | "Combine situation, action, and measurable result into a single richer line" |

The 4+ case is intentional — instead of "be brief" (which produces weaker writing), the model is told to write fewer but richer bullets. Each clause must carry weight.

Always includes: "PRESERVE ALL EXPERIENCES: every experience in the input must appear in the output. Do not drop, merge, or omit any experience, even older ones. Reorder by relevance is fine; removal is not." (Earlier prompts allowed dropping older experiences to hit one page — deleted after producing lazy outputs.)

---

### Stage 4 — Post-generation validation + retry
Same self-correction loop as parse:
1. `extractJSON()` strips markdown fences and parses
2. `improvedCVSchema` / `tailoredCVSchema` validates (Zod)
3. On failure: re-call Gemini once with Zod errors appended
4. Second failure → throw, mark session failed, show Spanish error message

Both schemas require skills to be an object of arrays (categorized form), not a flat array — forcing the LLM to actually do the categorization step rather than passthrough.

---

### Stage 5 — One-page enforcement (purely local, no second LLM call)
Modules: `one-page-enforcer.ts`, `page-fit.ts`

If user ticked "Fit on one page":
1. **Render-char count** — `countRenderableChars()` sums all fields. Budget: `ONE_PAGE_CHAR_BUDGET = 2800` (empirically tuned for Aptos 11pt with current margins)
2. **Fit check** — under budget? Ship it
3. **Local trim** — `trimToFit()` repeatedly drops the shortest bullet across all experiences until under budget. Tie-break: earliest experience, earliest bullet. Hard rule: every experience keeps at least one bullet.
4. If still over: return with soft warning "El CV no pudo reducirse a 1 página."

No second LLM call. A "be more concise" second call used to exist — deleted because it consistently produced weaker outputs. Now the LLM always writes its best; trimming is purely mechanical.

---

### Stage 6 — Document generation (deterministic)
Modules: `renderable-document.ts` → `docx-generator.ts` / `pdf-generator.ts`

Structured CV passes through a platform-agnostic intermediate (`RenderableDocument`) before rendering into DOCX or PDF. Section headings translate based on `target_language` (Experiencia / Experience / Experiência / Expérience). Both generators iterate over a `DocumentBlock` discriminated union — DOCX and PDF are guaranteed structurally identical: same content, same order, same headings, different rendering engines.

---

### Why this pipeline beats "paste into ChatGPT" — the marketing table

| Concern | What WorqAI does |
|---|---|
| Structured output reliability | Zod-validated JSON + one-shot self-correction at parse, improve, and tailor stages |
| Hallucinated facts | Companies/dates/institutions explicitly protected; only achievements may be embellished |
| Bullet quality | STAR format enforced, action-verb-led, quantification pushed — invisible to the reader |
| ATS compatibility | Flat document layout (no tables/columns), keywords woven into prose not stuffed |
| Keyword matching | Full job description handed to LLM; relevance scoring is contextual, not regex |
| Length control | Prompt-side bullet-count rules adapt to experience count; output never dropped, only mechanically shaved |
| Multi-language | Auto-detected at parse; document generator emits localized section headings |
| Reproducibility | Deterministic post-processing (trim, render) on top of the LLM's stochastic step |
